# Data Dictionary: Anchorpoint B2B Sales Dataset

Version: Phase 2, 2026-08-21. Covers all seven tables in `data/raw/`, generated by `src/generate_data.py` under `SEED = 42`. Row counts below are from the Phase 2 formal run; see `docs/project_context.md` for the dated entry recording emergent outcomes and `docs/validation/` for the corresponding validation report.

Reading rule: "generation rule" describes the mechanism step that produced a value, not just its statistical shape. For columns set inside `resolve_deal()`, the step number refers to the seven-step order of operations documented in that function's docstring in `src/generate_data.py`. Nothing in this file states an expected result; it describes how a column was produced, not what it measures. Findings belong in `docs/findings_summary.md` (Phase 3), not here.

## companies (900 rows)

One row per B2B company in Anchorpoint's addressable base. Not every company has a deal; `deals` and `sales_pipeline` draw company_id from this table.

| Column | Type | Meaning | Nulls | Generation rule |
|---|---|---|---|---|
| `company_id` | string | Unique identifier, `CO#####` | none | Sequential, assigned at generation |
| `company_name` | string | Synthetic company name | none | Combined from prefix/core/suffix word lists, cosmetic only, no mechanism dependency |
| `industry` | string | One of 10 B2B-relevant industries | none | Uniform draw from a fixed industry list, cosmetic |
| `region` | string | `US`, `EU`, or `APAC` | none | Weighted draw, `REGION_WEIGHTS = [0.62, 0.26, 0.12]`. Load-bearing: Confounder A (EU competitive entry) depends on this field |
| `employee_count` | int | Company headcount | none | Lognormal draw within a segment-specific band, clipped to that band. Bands: Enterprise 1,000 to 20,000 (median 3,000), Mid-Market 100 to 999 (median 300), SMB 10 to 99 (median 35). The company's segment is drawn first, in proportion to that segment's share of closed-deal attempts, then employee_count is drawn to match |
| `founding_date` | date | Company founding date | none | Segment-correlated year range (Enterprise 1995 to 2015, Mid-Market 2005 to 2020, SMB 2014 to 2024), cosmetic, no mechanism dependency |

**Note on segment.** `companies` carries no explicit segment column. Which segment's deals a company is eligible for is a deterministic function of `employee_count` (Enterprise >= 1,000, Mid-Market 100 to 999, SMB < 100, see `_segment_from_employee_count()`), recomputed wherever needed rather than stored, so it cannot drift out of sync with how the company was generated.

## sales_reps (30 rows)

The independent variable of the entire analysis. `has_enterprise_experience` and `playbook_type` are what the diagnosis rests on.

| Column | Type | Meaning | Nulls | Generation rule |
|---|---|---|---|---|
| `rep_id` | string | Unique identifier, `REP###` | none | Sequential |
| `rep_name` | string | Synthetic rep name | none | Role-labelled placeholder, cosmetic |
| `segment` | string | `Enterprise`, `Mid-Market`, or `SMB` | none | Fixed by rep cohort at generation (see composition below) |
| `hire_date` | date | Date the rep started | none | Founder-led reps: 2021-03-01. New Enterprise AEs: `ENTERPRISE_PUSH_DATE` (2025-01-01), all identical, a staffing event not a performance trigger. Mid-Market and SMB reps: uniform draw 2018 to 2022, always well before the earliest possible `opened_date` in `deals` so no rep is ever assigned a deal opened before their hire date |
| `prior_segment` | string | Where the rep came from before this role | founder-led and Mid-Market/SMB reps only | New Enterprise AEs only: 6 of 8 marked `SMB` or `Mid-Market` (promoted internally), 2 marked `External` (hired from non-enterprise roles). Null for founder-led and tenured Mid-Market/SMB reps, who were not repositioned into their current role |
| `has_enterprise_experience` | bool | Whether the rep has run a multi-stakeholder enterprise motion before | none | True only for the 2 founder-led reps. False for all 8 new Enterprise AEs and all Mid-Market/SMB reps, since experience is only meaningful relative to the Enterprise motion |
| `playbook_type` | string | `multi_threaded` or `single_threaded` | none | Direct function of `has_enterprise_experience`: `multi_threaded` when True, else `single_threaded` |
| `quota_annual_usd` | int | Annual new-business quota | none | Enterprise AEs (founder-led and new): $800,000, Bridge Group median enterprise AE quota, locked in `case_study_scenario.md`. Mid-Market: $400,000. SMB: $200,000. The Mid-Market and SMB figures are not locked upstream; they are an implementation assumption scaled to each segment's smaller average deal size, logged in `docs/decisions.md`, 2026-08-21 |
| `is_founder_led` | bool | Whether the rep is one of the two original founder-led Enterprise reps | none | True for exactly 2 rows, both Enterprise |

**Composition (30 total):** 2 founder-led Enterprise reps, 8 new Enterprise AEs, 10 Mid-Market reps, 10 SMB reps.

## deals (2,200 rows)

One row per closed opportunity, won or lost. Grain: one row per closed attempt: a company with three closed opportunities appears three times. This is the table `resolve_deal()` writes to, and it is the only table with no win rate anywhere in its generation code; every deal's outcome is a consequence of the mechanism, not an assignment.

| Column | Type | Meaning | Nulls | Generation rule |
|---|---|---|---|---|
| `deal_id` | string | Unique identifier, `D######` | none | Sequential, assigned in generation order (Enterprise pre-push, Enterprise post-push, Mid-Market, SMB) |
| `company_id` | string | Foreign key to `companies` | none | Drawn with replacement from companies whose derived segment matches the deal's segment |
| `rep_id` | string | Foreign key to `sales_reps` | none | Enterprise pre-push: always a founder-led rep. Enterprise post-push: a founder-led rep with probability `FOUNDER_LED_POST_PUSH_SHARE = 0.12` (the 2026-08-21 contemporaneous control amendment), otherwise one of the 8 new AEs. Mid-Market/SMB: drawn from that segment's tenured rep pool |
| `segment` | string | `Enterprise`, `Mid-Market`, or `SMB` | none | Fixed per generation batch. Exact counts: Enterprise 420, Mid-Market 760, SMB 1,020, matching the locked mix in `data_model.md` |
| `region` | string | `US`, `EU`, or `APAC` | none | Inherited from the deal's `company_id`, not drawn independently |
| `acquisition_channel` | string | `Direct Sales`, `Inbound`, or `Partnerships` | none | Weighted draw from `CHANNEL_MIX_BY_SEGMENT`, segment-specific (Enterprise is 88% Direct Sales) |
| `deal_size_usd` | float | Deal value in USD | none | Lognormal draw clipped to the segment's range, with mu calibrated iteratively so the post-clip mean lands near `deal_size_avg` (see `_calibrate_deal_size_mu`). Deals opened on or after `PRICE_INCREASE_DATE` (2025-08-01) are scaled by `(1 + PRICE_INCREASE_PCT)`, a 12% list price increase applied uniformly across segments |
| `opened_date` | date | Date the opportunity was opened | none | Drawn from a window extended 12 months before `WINDOW_START` (to 2023-07-01), weighted by `SEASONALITY_BY_MONTH`. Enterprise opens are split into a pre-push pool (before `ENTERPRISE_PUSH_DATE`) and a post-push pool, at roughly a 25/75 ratio. The wide range and the downstream filtering rule below are what avoid censoring bias (see AGENT-BUILD-GUIDE.md 7.1) |
| `close_date` | date | Date the opportunity closed, won or lost | none | `opened_date + sales_cycle_days`. Deals whose resulting `close_date` falls outside `[WINDOW_START, WINDOW_END]` are discarded and a fresh deal is drawn in their place, so the exported table is exactly the deals that closed in the window. Discarding is based purely on window membership, never on any characteristic correlated with the outcome |
| `deal_won` | bool | Whether the deal closed won | none | Mechanism step 7. True only if the deal passed qualification (step 3), engaged the buying group before buyer patience ran out (step 5), and won the competitive test (step 6) |
| `loss_reason` | string | `unqualified`, `stalled_no_decision`, `lost_to_competitor`, or null for wins | wins only | Set by whichever mechanism step ends the deal: step 3 (`unqualified`), step 5 (`stalled_no_decision`, the primary failure path for the new Enterprise team), or step 6 (`lost_to_competitor`) |
| `stakeholders_required` | int | Size of the buying group this deal needed to engage | none | Mechanism step 1. `max(1, round(lognormal))`, median approximately 6 for Enterprise (Gartner: 6 to 10 stakeholders in complex B2B), scaled modestly by where `deal_size_usd` falls within the segment's range |
| `stakeholders_engaged` | int | How many stakeholders were actually engaged before the deal ended | none | Mechanism steps 3, 5, 6, 7. 0 for `unqualified` (never began engaging). For `stalled_no_decision`, `min(stakeholders_required, touch_rate x timeout_months)`, always less than required by construction. Equal to `stakeholders_required` for `lost_to_competitor` and won deals, since both fully engaged the group before the outcome was decided |
| `sales_cycle_days` | int | Days from `opened_date` to `close_date` | none | Mechanism steps 2 through 7, converted from the mechanism's month-denominated cycle length via `round(cycle_months x 30.44)`. Reconciles exactly to the sum of `deal_stage_history.days_in_stage` for the same `deal_id` |

**Note.** There is deliberately no `days_in_stage` column here (Phase 1's ambiguous scalar). Per-stage timing lives in `deal_stage_history`.

## deal_stage_history (5,824 rows)

One row per stage a deal passed through. A deal that failed qualification has one row; a deal that reached Negotiation has four. Exists to make Question 4 (where deals stall) answerable at all.

| Column | Type | Meaning | Nulls | Generation rule |
|---|---|---|---|---|
| `deal_id` | string | Foreign key to `deals` | none | One to many with `deals` |
| `stage` | string | `Prospecting`, `Qualified`, `Proposal`, or `Negotiation` | none | `unqualified` deals get a single `Prospecting` row only, since they never cleared qualification. All other deals (`stalled_no_decision`, `lost_to_competitor`, won) get all four stages in order |
| `entered_date` | date | Date the deal entered this stage | none | First stage's `entered_date` equals the deal's `opened_date`; each subsequent stage's `entered_date` equals the prior stage's `exited_date` |
| `exited_date` | date | Date the deal left this stage | last stage of an active pipeline deal would be null, but this table only covers closed deals, so always populated here | `entered_date + days_in_stage` |
| `days_in_stage` | int | Days spent in this stage | none | Total `sales_cycle_days` allocated across the deal's stages by fixed proportion, with the remainder from integer rounding assigned to the last stage to guarantee an exact reconciliation. Normal outcomes: 12% Prospecting, 18% Qualified, 35% Proposal, 35% Negotiation. Stalled outcomes: 8% / 12% / 30% / 50%, weighting more of the deal's time into Proposal and Negotiation, since that is where the stakeholder-engagement mechanism actually plays out and where the new Enterprise team's deals die |

**Reconciliation.** `sum(days_in_stage)` per `deal_id` equals that deal's `sales_cycle_days` exactly (0 day drift confirmed in validation, not just within the 1 day tolerance the check allows).

## customers (616 rows)

One row per won deal. Row count is not an independent parameter, it equals `deals.deal_won.sum()` exactly.

| Column | Type | Meaning | Nulls | Generation rule |
|---|---|---|---|---|
| `customer_id` | string | Unique identifier, `CUST#####` | none | Sequential |
| `deal_id` | string | Foreign key to `deals`, only ever a won deal | none | One to one with the won subset of `deals` |
| `segment` | string | Inherited from the deal | none | Copied from `deals.segment` |
| `cohort_month` | date | First day of the month the deal closed | none | Truncated from `deals.close_date` |
| `annual_contract_value` | float | ACV in USD | none | Equal to the originating deal's `deal_size_usd` |
| `churn_date` | date | Date the customer churned | active customers | Annual churn rate (`SEGMENTS[segment]["annual_churn"]`) converted to a monthly hazard, `1 - (1 - annual_churn)^(1/12)`. Months to churn drawn from a geometric distribution on that hazard. If the draw falls within the customer's observed window (`close_date` to `WINDOW_END`), `churn_date` is set and the customer is marked inactive; otherwise the customer is right-censored as active at window end |
| `months_retained_observed` | int | Months observed, whether still active or churned | none | Months to churn if churned within the window, otherwise the full observed window length (`(WINDOW_END - close_date)` in months) |
| `is_active_at_window_end` | bool | Whether the customer had not churned by `WINDOW_END` | none | Exact negation of whether `churn_date` is set |

**Documented limitation, not engineered away.** Enterprise produced 6 observed churn events in the Phase 2 run (Mid-Market 24, SMB 100). Enterprise retention cannot be measured from this data at any volume achievable inside a realistic window; Phase 3 must use benchmark churn with a stated sensitivity range for Enterprise rather than a measured curve. See `docs/decisions.md`, 2026-08-20 and 2026-08-21 entries.

## sales_pipeline (400 rows)

Open opportunities as of `WINDOW_END`, not yet closed. Carries forward-looking evidence of the same mechanism visible in `deals`, before it lands in closed-won or closed-lost.

| Column | Type | Meaning | Nulls | Generation rule |
|---|---|---|---|---|
| `opportunity_id` | string | Unique identifier, `OPP#####` | none | Sequential |
| `company_id` | string | Foreign key to `companies` | none | Drawn from companies matching the opportunity's segment, same mechanism as `deals.company_id` |
| `rep_id` | string | Foreign key to `sales_reps` | none | Enterprise opportunities: founder-led rep with probability 0.12 (same share as post-push `deals`), otherwise one of the 8 new AEs. Mid-Market/SMB: drawn from the tenured pool |
| `segment` | string | `Enterprise`, `Mid-Market`, or `SMB` | none | Drawn in proportion to each segment's share of closed-deal volume |
| `region` | string | `US`, `EU`, or `APAC` | none | Inherited from `company_id` |
| `acquisition_channel` | string | `Direct Sales`, `Inbound`, or `Partnerships` | none | Same weighted draw as `deals.acquisition_channel` |
| `stage` | string | `Prospecting`, `Qualified`, `Proposal`, or `Negotiation` | none | Weighted draw. Enterprise opportunities owned by a new AE skew toward Proposal/Negotiation (75% combined weight); Enterprise owned by a founder-led rep and Mid-Market/SMB are closer to even across all four stages (45% and 50% combined Proposal/Negotiation respectively) |
| `stage_entered_date` | date | Date the opportunity entered its current stage | none | `WINDOW_END - days_in_current_stage` |
| `days_in_current_stage` | int | Days the opportunity has sat in its current stage | none | Lognormal draw. Enterprise opportunities owned by a new AE, in Proposal or Negotiation specifically, draw from a higher-median distribution (median 70 days) than every other case (median 25 days), capped at 400 days. This is the column that shows Enterprise pipeline coverage is inflated by stuck opportunities before that shows up in closed-lost data |
| `forecast_close_date` | date | CRM-forecasted close date | none | `WINDOW_END` plus a uniform 15 to 120 day offset, cosmetic |
| `forecast_amount_usd` | float | Forecasted deal value | none | Same calibrated lognormal draw as `deals.deal_size_usd`, by segment |
| `win_probability_pct` | int | CRM-displayed win probability for the current stage | none | Fixed stage convention regardless of who owns the deal: Prospecting 10, Qualified 25, Proposal 50, Negotiation 70. Deliberately identical for a healthy and a stuck opportunity in the same stage, since that is the point: the dashboard field does not know a deal is stuck, only `days_in_current_stage` reveals it |

## sm_spend (78 rows)

Monthly sales and marketing spend by segment, 26 months times 3 segments. Replaces an annual scalar so Phase 3 can compute period-correct CAC.

| Column | Type | Meaning | Nulls | Generation rule |
|---|---|---|---|---|
| `month` | date | First day of the month | none | One row per calendar month from `WINDOW_START` to `WINDOW_END` inclusive, per segment |
| `segment` | string | `Enterprise`, `Mid-Market`, or `SMB` | none | Fixed, one row per segment per month |
| `spend_usd` | float | S&M spend for that segment in that month | none | `MONTHLY_SM_SPEND_BY_SEGMENT[segment]` (Enterprise $266,667/mo, Mid-Market $150,000/mo, SMB $100,000/mo, from the annual figures locked in `case_study_scenario.md`). Enterprise spend before `ENTERPRISE_PUSH_DATE` is scaled down by `ENTERPRISE_PRE_PUSH_SPEND_FRACTION` (0.18), reflecting founder-led coverage with no dedicated team. Enterprise spend does not scale down after the push even as its win rate falls: that rigidity is the financial core of the case study, fixed cost against falling yield |

## Cross-table reconciliation, all confirmed in the Phase 2 validation run

- `len(deals) == 2,200`, `len(sales_pipeline) == 400`, exact
- `len(customers) == deals.deal_won.sum()`, exact (616 in this run)
- Zero orphan `company_id` or `rep_id` in `deals` or `sales_pipeline`
- Zero `customers.deal_id` missing from `deals` or pointing at a lost deal
- Every `deal_stage_history.deal_id` present in `deals`
- `deal_stage_history.days_in_stage` summed per deal equals that deal's `sales_cycle_days` exactly (0 day drift)
- Every `deals.close_date` inside `[2024-07-01, 2026-08-31]`
- Zero Enterprise deals opened before `ENTERPRISE_PUSH_DATE` assigned to a rep hired on or after it
- Realized mean `deal_size_usd` within 15% of target for all three segments
- Re-running the generator under `SEED = 42` reproduces content-identical CSVs, confirmed via SHA-256 hash across two separate output directories

Full validation report: `docs/validation/validation-phase2-20260821-084044.md`.
